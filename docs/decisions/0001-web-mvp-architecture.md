# ADR-0001：使用 FastAPI 服务端渲染单体实现 Web MVP

## 状态

Proposed

## 日期

2026-08-07

## 背景

现有项目是一个约 700 行的 Python Tkinter 桌面原型。目标是在 2–3 小时内将其转化为可在线访问、可测试、可部署并适合 AI/FDE 面试展示的 Web MVP。首版需要调用 DeepSeek 和 Tavily，展示结果及搜索过程，但不需要账号、数据库或复杂前端状态。

关键约束：

- 时间预算非常有限；
- 现有可复用逻辑使用 Python；
- 外部 API 可能超时或部分失败；
- 项目需要有清晰 API 契约和自动化测试；
- 部署和本地启动必须简单、可复现。

## 决策

使用 FastAPI 构建单个 Python 服务，同时提供 JSON API、Jinja2 页面和静态资源。搜索服务采用异步适配器接口，DeepSeek、Tavily 等与核心编排逻辑分离。应用通过单个 Docker 镜像部署到国内轻量服务器（阿里云/腾讯云）。

MVP 使用服务端渲染页面加少量原生 JavaScript，不拆分独立 React 前端，也不引入数据库。

## 备选方案

### React/Vite + FastAPI 双应用

- 优点：前端交互能力和工程边界更强；
- 缺点：需要两套构建、跨域配置和可能的双服务部署；
- 未选择原因：在 2–3 小时约束下会挤压错误处理、测试和部署时间。

### Streamlit 或 Gradio

- 优点：最快形成可交互 AI Demo；
- 缺点：API 契约、界面控制和生产工程展示相对有限；
- 未选择原因：项目需要突出 FDE 的系统集成和服务边界，而不仅是模型演示。

### 保留 Tkinter 并打包桌面应用

- 优点：改动最小，可复用全部界面代码；
- 缺点：无法通过 URL 直接体验，部署与面试演示不方便；
- 未选择原因：与“在线访问”目标冲突。

### Serverless Functions

- 优点：部署轻量、按请求计费；
- 缺点：外部搜索扇出可能触发执行时限，Python 依赖和冷启动需要额外处理；
- 未选择原因：单容器更直观，便于本地复现和健康检查。

## 后果

正面影响：

- 复用 Python 经验和部分搜索逻辑；
- 一个仓库、一个进程、一个镜像即可运行；
- FastAPI 自动提供 OpenAPI，便于展示接口设计；
- 可使用依赖注入和假适配器稳定测试外部失败；
- 后续仍可替换为 React 前端，而不改变核心搜索服务。

负面影响：

- 页面交互丰富度低于独立前端；
- 应用内同时承担页面、API 和编排职责，规模扩大后需要拆分；
- 国内轻量服务器需自行维护（系统更新、HTTPS、备案），且需购买服务器；
- 进程内状态和限流无法支持多实例一致性。

## 重新评估条件

出现下列任一情况时重新评估本决策：

- 需要复杂客户端状态、账号体系或多页面交互；
- 日均请求量或团队规模要求独立部署前后端；
- 搜索任务超过同步请求时限，需要队列和后台任务；
- 需要持久化历史、反馈或排名评估数据。
