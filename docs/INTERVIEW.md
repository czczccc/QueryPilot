# QueryPilot 面试 Q&A 准备

> 面向 FDE / AI 应用岗位面试。每个问题给出「回答要点」，全部基于本项目真实实现，可直接背诵或用自己语言复述。

## 1. 介绍一下这个项目（30 秒版本）

> "QueryPilot 是一个 AI 搜索与链接验证引擎。用户用自然语言描述要找的资源，系统用 DeepSeek 解析意图并生成多组查询词，然后并发调用 Tavily API、Bing 中文、垂直搜索站三个引擎召回候选，从中提取目标平台的分享链接，最后用逆向的两步 API 对每条链接做严格有效性验证，把'有效/已失效'区分出来再展示。项目是 FastAPI 单体，48 个测试，Docker 部署在公网服务器上。"

## 2. 你解决了什么真实问题？

- 传统搜索返回大量"看起来存在"的链接，但很多实际已删除/过期/被举报；
- 只查 HTTP 状态码是假象——分享平台对不存在的链接也返回 200（静态壳页）；
- 用户需要的是**验证过真实可用**的链接清单，而不是自己挨个点击试错。

## 3. LLM 输出怎么保证可靠？（必问）

- 不信任 LLM 裸输出：先 `_coerce` 归一化（类型清洗、截断超限字段、过滤空值、非法枚举映射兜底），再交给 **Pydantic `model_validate`** 做严格类型校验；
- 校验不通过、超时、HTTP 错误、无 key → 全部走**规则降级**（关键词清洗 + 默认查询词），系统仍然可用，响应里带 `fallback_used` 标记；
- 关键设计：LLM 是"增强"不是"依赖"，坏输出不会污染下游搜索。

## 4. 为什么选 DeepSeek？

- OpenAI 兼容 API，`deepseek-v4-flash` 便宜、快、中文好，适合意图解析这种轻任务；
- 项目里通过 `response_format: json_object` 强制 JSON 输出 + 模型名大小写敏感（`deepseek-v4-flash`）这些细节都踩过坑处理过；
- 换模型零成本——解析器是独立模块，只要改模型名。

## 5. 为什么不用通用搜索 API，要自己解析 Bing HTML？

- 覆盖中文资源场景时，免费/低成本方案更可控；Tavily 有配额成本；
- Bing 抓取是**增强召回面**的手段，配合 Tavily 主引擎；
- 代价是 HTML 结构脆弱——处理方式是解析逻辑集中在一个函数里，实测新版 Bing 把链接内嵌进标题（`<h2>` 文本里），已适配并有回归测试；
- 面试延伸：可以聊"第三方依赖脆弱性"的工程取舍（稳定 API 为主 + 免费抓取为辅 + 失败降级）。

## 6. 链接验证具体怎么做？为什么状态码不够？（核心亮点）

- 弱验证：`GET pan.quark.cn/s/xxx` 对有效/失效链接**都返回 200**（静态壳页 9602 字节完全一致），所以状态码毫无区分度；
- 严格验证（逆向分享页前端 share.js 得到两步 API）：
  1. `POST sharepage/token` 取 stoken——分享不存在/已失效返回 HTTP 404（code 41006/41011）；
  2. `GET sharepage/detail` 带 stoken 查文件列表——有文件且 `share.status==1` 判有效，无文件判失效；
- 网络异常/解析失败判"待确认"，不武断；
- 效果：旧逻辑 17 条"可达"链接里 16 条实际已失效，新逻辑准确筛出。

## 7. 并发怎么控制？（常问）

- `asyncio.gather` + `Semaphore` 限流：Tavily 查询变体、深度抓取（4 路）、链接验证（8 路）分别限流，避免打爆外部服务；
- 每个外部调用都有超时（默认 8 秒，验证 8 秒），不会无限等待；
- 前端还有 120 秒 AbortController 保护，超时给明确文案而不是转圈。

## 8. 部分失败怎么处理？

- 一个引擎失败 → 其他引擎结果照常返回，响应 `providers` 里标明 `error` 和错误类型；
- 全部引擎失败 → 受控 503，响应体只有友好文案，**不泄漏内部堆栈/错误类型**；
- DeepSeek 失败 → 规则降级继续搜。

## 9. 可观测性做了哪些？

- 每次响应带 `request_id`（uuid）；
- `providers` 数组：每个引擎的 status / result_count / duration_ms / error_type；
- `metrics`：总耗时、原始数、去重数、是否降级；
- 前端把指标展示出来——面试官能直接看到"这次搜索 3 个引擎各花了多久"。

## 10. 安全上做了什么？

- 密钥只走环境变量/服务器 `.env`，`config.json`、`.env` 被 gitignore，git 历史零密钥（有审计）；
- 前端全部 `textContent` 渲染（防 XSS），外链 `target=_blank` + `rel=noopener noreferrer`；
- 只接受 `http/https` 链接；
- **已知局限（诚实说）**：深度抓取的目标 URL 来自搜索源，当前未做内网 IP/SSRF 过滤——如果面试官追问，可以说"这是已知边界，生产化会加 URL scheme 白名单 + 内网网段过滤"。

## 11. 测试怎么写的？为什么 48 个测试没花一分钱？

- 所有外部调用用 `httpx.MockTransport` 假客户端注入，不碰真实 API；
- 覆盖：LLM 各种失败路径、正则提取、验证三分支、Bing 解析（含新结构回归）、编排部分成功/全失败、API 422/503；
- 快（2 秒内跑完）、确定、可重复——CI 里每次 push 都跑。

## 12. 部署链路？

- Dockerfile 多阶段，非 root 用户运行；
- 国内服务器构建用阿里云 pip 镜像（`PIP_INDEX_URL` build-arg），解决默认 PyPI ~34KB/s 卡死问题；
- `docker compose up -d --build` 一键部署，`.env` 管密钥；
- 公网 http://124.223.112.9:8000 可访问，`/health` 探活；
- GitHub Actions：push 触发 pytest + ruff + docker build。

## 13. 项目里遇到的最大挑战？

> 首选回答（真实经历）：
> "链接验证。一开始以为查 HTTP 状态码就够了，实测发现分享平台对不存在的链接也返回 200 静态壳页，17 条'可达'链接 16 条实际失效。我抓了分享页前端的 share.js（1.1MB），从 JS 里逆向出真实的 token/detail 两步 API，用 stoken + 文件列表判断真实有效性，才把假象解决。"

## 14. 如果重做，会改进什么？

- 深度抓取加 SSRF 防护（内网 IP 过滤）；
- 进程内限流 + 请求 ID 日志贯穿；
- 更多垂直搜索站（统一 SearchProvider 接口已预留）；
- 加缓存层减少重复搜索的外部调用。

## 15. 一分钟后你要会说的关键词

**意图解析 + Pydantic 校验 + 规则降级 / 多源聚合 + 受控并发 + 部分成功 / 严格链接验证（token+detail 两步 API）/ request_id 可观测 / MockTransport 零成本测试 / Docker 国内镜像部署 / 壳页 200 假象**
